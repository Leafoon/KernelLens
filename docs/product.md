# 产品需求与范围

本文定义产品目标、需求和业务验收边界。当前实现状态以 [当前能力与验证范围](status.md) 为准；本文描述目标能力，不表示能力已实现。

## 项目身份

| 项目 | 定义 |
| --- | --- |
| 中文名称 | KernelLens：面向 TileLang 的算子开发与优化智能体 |
| 英文名称 | KernelLens Agent |
| Repository | kernellens-agent |
| 简历项目名称 | KernelLens：基于状态与证据约束的算子开发 Agent |
| 一句话介绍 | 根据需求生成 TileLang 算子，调查问题并提出优化候选，结合源码和执行证据追踪结果 |
| 核心用户 | 算子开发者、推理优化工程师，以及正在学习 TileLang 的开发者 |

## 真实问题与价值假设

算子开发需要同时对齐计算语义、输入布局、API 版本、设备能力与测试结果。资料分散，生成的代码可能引用过时 API；编译成功也不能证明数值正确或性能改善。

KernelLens 接收用户需求或已有实现，通过工具查证、形成候选并给出可执行的实验说明。初期用户负责把算子移交服务器执行，回传结果后继续迭代。减少无效尝试和资料检索时间是待评测的业务假设，不作为已实现收益宣传。

## 用户场景与验收契约

| 场景 | 输入 | 交付 | 合格条件 |
| --- | --- | --- | --- |
| GEN：生成 | 计算语义、shape、dtype、布局、设备、精度和资源约束 | 算子候选、实现依据、正确性测试与执行说明 | 覆盖已确认需求；关键 API 有证据；明确尚未运行的检查 |
| OPT：优化 | 已有代码、优化目标、设备、可选 baseline 数据 | 瓶颈假设、优化候选、改变了什么、对照实验方案 | 保持计算契约；解释可证伪的优化假设；没有实测不得宣称加速 |
| DBG：诊断 | 代码、错误或错误输出、环境与源码版本 | 调查结论、支持及反驳证据、修复建议 | 证据可追踪；缺少信息时请求补充或明确无法判断 |
| VERIFY：验证反馈 | 代码标识、环境、测试参数、日志与结果 | 各检查状态、基线对比、剩余问题 | 对应正确的代码与环境；区分用户报告和 Agent 实际执行 |

创建任务时明确任务类型。输入模糊时先澄清，而不是默认进入诊断。任务中可以基于新证据切换调查策略，但不能悄悄改变用户目标。

## Agent Necessity Analysis

| 层次 | 能力与定位 |
| --- | --- |
| 普通 Python | 文件、语法、路径、参数与证据标识检查；承担确定性逻辑 |
| 单次 LLM | 解释给定材料；作为低复杂度基线 |
| 固定 Workflow | 固定检索、检查与报告步骤；作为主要对照基线及外层约束 |
| Single Agent | 根据 Observation 选择下一次查询、修改候选或请求信息；推荐方案 |
| Multi-Agent | 需要独立权限、上下文或专门职责时才评估；当前不需要 |

动态决策的价值在于：API 查询、设备确认、源码调查、候选修改的下一步取决于已经发现的证据。权限、预算和完成条件仍由程序决定。若某类任务的固定 Workflow 效果相同且更便宜，就保留固定路径。

## MVP / V1 / V2

| 版本 | 必须交付 | 不包含 |
| --- | --- | --- |
| MVP（Phase 1–5） | 基础 GEMM 的生成、优化建议、诊断；CLI；单 Agent；只读证据工具；静态检查；结构化报告；产物及运行记录；预算；基线评测 | 自动执行用户代码、自动修改用户仓库、多用户后台系统、已验证的性能承诺 |
| V1（Phase 6–7） | API；显式恢复与取消；轨迹查询；人工服务器结果导入；代码与环境关联；修复反馈闭环；ARM64 部署与 CI | 无真实执行证据却标记已验证；未经需求证明的分布式组件 |
| V2（Phase 8，按需） | 受控执行器；GPU 自动验证；检索／模型／框架优化；更多算子类型 | 为了简历而预设所有扩展必做 |

MVP 可记录用户提供的日志为输入证据；正式验证结果导入契约在 V1 完善。V1 仍可由人执行服务器实验，完整 Agent 产品不以拥有自动 GPU Runner 为前提。

## 需求清单

| 类别 | MVP 要求 | 后续演进 |
| --- | --- | --- |
| Business | 让三个主要任务可追踪、可验收；验证效率与质量收益 | 依据真实用户案例扩展 |
| Functional | 明确需求、检索、提出行动、生成候选、检查、输出报告 | 验证反馈与服务接口 |
| Non-functional | 原生 ARM64、可复现、运行有界、失败可解释 | 可部署、可恢复、负载与保留策略 |
| Agent Capability | 选择工具、维护假设、结合 Observation 更新行动 | 复杂策略与模型比较 |
| Data | 来源、版本、位置和内容标识；原材料可追踪 | 漂移检测与案例管理 |
| Model | 工具调用、结构化结果、usage；一个实际 provider | 基于数据增加替代模型 |
| Tool | Schema、路径边界、超时、错误分类、输出限制 | MCP 与受控执行适配器 |
| Memory | 当前任务事实、候选、步骤与运行记录 | 经确认的历史案例复用 |
| Context | 分离指令和数据；限制每轮片段及输出 | 通过评测优化压缩 |
| Workflow | 生成／优化／诊断目标明确；出口与终止原因可检查 | 等待、恢复与取消 |
| Error Handling | 区分模型、工具、输入、业务失败与预算耗尽 | 安全恢复与幂等行为 |
| Evaluation | 单次 LLM、固定 Workflow、Agent 对照 | 优化与回归报告 |
| Observability | 步骤、工具、结果摘要、耗时、错误、usage | 轨迹界面与导出 |
| Security | 限定读取范围；密钥隔离；材料视为不可信输入 | 服务鉴权和执行隔离 |
| Extensibility | 模型、工具、证据和存储边界清晰 | 有实际需求才替换实现 |

## 业务不变量

1. 静态检查通过不代表算子可编译、数值正确或运行更快。
2. 报告完成和算子验证通过是不同维度。
3. 未执行的检查必须为未执行，不能使用成功默认值。
4. 性能改善要求对应 baseline、代码、环境、工作负载和测量方法；不跨不一致条件比较。
5. 没有足够证据时，保留假设、请求信息或停止；不通过降低报告要求来伪造完成。
6. 系统自主生成算子是产品功能；开发本系统的核心 Agent 逻辑由用户亲手实现。
